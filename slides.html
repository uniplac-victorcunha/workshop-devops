CI/CD — automatizando o caminho até o usuário

A resposta do DevOps para o "funciona na minha máquina"

Em vez de fazer build, testar e subir manualmente (e torcer pra dar certo), a equipe configura uma esteira automática que faz isso a cada alteração de código.

🔄 CI — Continuous Integration

"Integrar código com frequência"

Toda vez que um dev faz commit, o sistema compila e roda os testes sozinho. Se algo quebra, o time sabe em minutos — não em semanas.

Resolve: "ninguém viu que meu código quebrou o do colega"

🚀 CD — Continuous Delivery

"Entregar com frequência e confiabilidade"

Se o código passa em todos os testes, ele já fica pronto para subir em produção — sem reuniões, sem "sextou". Em alguns times, sobe automaticamente.

Resolve: "tenho medo de subir em produção"

💡 Juntos, CI + CD formam um pipeline — uma sequência de etapas automáticas. Vamos ver o pipeline →

Containers e Docker

Containers — a marmita do software

O fim do "funciona na minha máquina"

O CI/CD automatiza o caminho. Mas e se a versão do Node do seu notebook for diferente da do servidor? E se faltar uma biblioteca? É aqui que entram os containers.

Um container é como uma marmita 🍱. Você coloca o código, as dependências e as configurações juntos numa caixa fechada. Essa marmita funciona igualzinho no seu notebook, no servidor da empresa e na nuvem.

🏢 Máquina Virtual (VM)

  • Sistema operacional completo dentro
  • Tamanho: vários GB
  • Inicialização: ~2 minutos
  • Como um prédio inteiro para 1 pessoa

📦 Container Docker

  • Compartilha o SO do host
  • Tamanho: dezenas de MB
  • Inicialização: segundos
  • Como um apartamento: estrutura compartilhada

💡 Por isso containers e CI/CD andam juntos: o pipeline gera uma imagem de container, e essa mesma imagem é a que vai pra produção. Sem surpresas.

Docker — os comandos essenciais

Do zero ao container rodando em 3 passos

Passo 1 — O Dockerfile (a receita do container):

FROM node:18-alpine        # imagem base
WORKDIR /app               # pasta de trabalho
COPY . .                   # copia o código
RUN npm install            # instala dependências
CMD ["node", "server.js"]  # comando para iniciar

Passo 2 — Construir e rodar:

docker build -t minha-app .        # cria a imagem
docker run -p 3000:3000 minha-app  # sobe o container

Passo 3 — docker-compose (sobe tudo junto):

docker-compose up   # frontend + backend + banco de uma vez
docker ps           # lista o que está rodando
docker logs api     # vê os logs do container "api"

Observabilidade

Observabilidade — saber o que acontece sem adivinhar

Você tem 15 containers rodando. Um usuário reclama. E agora?

Containers são ótimos pra rodar muita coisa em paralelo, mas multiplicam a complexidade: em vez de 1 sistema pra investigar, você tem 15. Sem ferramentas, virou caça ao tesouro.

🚦 Monitoramento

"Está funcionando?" — sim ou não

Como uma luz de check-engine no carro: avisa que tem problema, mas não diz onde nem por quê.

🔬 Observabilidade

"O que está acontecendo e por quê?"

Como um mecânico com aparelho de diagnóstico: vê qual peça, qual falha, desde quando.

🎯 Observabilidade é a habilidade de fazer perguntas novas ao sistema sem precisar mudar o código.

Os 3 pilares da observabilidade

Cada um responde uma pergunta diferente — e juntos, contam a história inteira

📊

Métricas

"O quê está acontecendo?"

Números ao longo do tempo. Servem para detectar.

Ex: CPU em 82%, 1.200 req/s, 5 erros na última hora.

🔧 Prometheus
📝

Logs

"O que aconteceu, exatamente?"

Registros textuais com timestamp. Servem para entender.

[ERROR] 14:32:01 — Falha ao conectar com banco

🔧 Loki
🔗

Traces

"Onde foi e qual o caminho?"

Rastreamento de uma requisição. Servem para localizar.

Checkout → Auth (12ms) → Pedidos (8ms) → Banco (380ms) ⚠

🔧 Tempo

🔍 Como os três trabalham juntos numa investigação real:

Métrica avisa "tempo de resposta subiu 10×" → Log mostra "erro de conexão com banco às 14:32" → Trace aponta "requisição travou na chamada ao banco"

Investigação que durava horas vira questão de minutos.

As ferramentas que fazem isso acontecer

Stack LGTM — o padrão open source do mercado

📊 Prometheus

Coleta e armazena métricas. Pergunta aos serviços: "quanto de CPU você está usando?"

📝 Loki

Agrega logs de todos os containers. "Prometheus, mas para logs." Criado pelo Grafana Labs.

🔗 Tempo

Registra o caminho das requisições. Mostra onde cada millisegundo foi gasto.

📺 Grafana

O painel que une tudo. Conecta Prometheus + Loki + Tempo em um único dashboard.

✨ Tudo open source e gratuito. Usado por CERN, PayPal, eBay e mais de 20 milhões de usuários.
No lab daqui a pouco, você vai abrir o Grafana e ver métricas reais saindo dos seus containers. →
